# Research: Physical Game Controllers

**Feature**: `034-game-controllers` | **Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

Each entry gives the decision, why, and what was rejected. Items marked **UNVERIFIED** rest on community reports rather than a Microsoft primary source and carry a validation task.

## R1. Device APIs: XInput 1.4 for Xbox-class, DirectInput 8 for the rest

- **Decision**: `xinput.lib` (imports `xinput1_4.dll`, in-box since Windows 8) for Xbox-class controllers; DirectInput 8 (`dinput8.lib`, `dxguid.lib`) for every other controller. Both libraries exist for x64 and ARM64 in SDK 10.0.26100.
- **Rationale**: DirectInput reports an Xbox controller's two triggers on one combined axis by design, and "In order to test the trigger values separately, you must use XInput" ([XInput and DirectInput](https://learn.microsoft.com/en-us/windows/win32/xinput/xinput-and-directinput)). XInput sees no non-Xbox device. Settled in the spec's clarifications.
- **Alternatives**: `xinput9_1_0` (reports every device as a gamepad subtype, lacks `XInputEnable`); Windows.Gaming.Input and GameInput (rejected in the spec clarification; GameInput also needs an installed runtime).

## R2. Focus (FR-033)

- **XInput**: `XInputEnable` is documented as deprecated because "game controller input is automatically enabled/disabled by the system based on the application window focus" on Windows 10+ ([XInputEnable](https://learn.microsoft.com/en-us/windows/win32/api/xinput/nf-xinput-xinputenable)). A 2025 Microsoft Q&A thread reports input continuing while unfocused; either way, the documented behavior cannot be relied on for background input.
- **Decision**: controller input applies only while Casso is active, and Xbox-class controllers always go through XInput (owner decision: XInput over background input). Casso decides activation itself from `WM_ACTIVATEAPP` rather than trusting either API's focus behavior, so both device kinds stop and resume at the same moment: on deactivation the controller source is released to rest in the mixer and samples are ignored until reactivation.
- **DirectInput**: `SetCooperativeLevel (hwnd, DISCL_BACKGROUND | DISCL_NONEXCLUSIVE)` on the controller thread's message-only window. Background acquisition is used only so acquisition does not depend on which Casso window is active; the activation gate above decides whether samples reach the game port ([SetCooperativeLevel](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee417921(v=vs.85))).
- **Measured 2026-09-11** on this machine, Xbox Series X|S controller over USB: XInput delivered 125 changes/s unchanged in all three cases -- the probe's main window active, a **second top-level window of the same process** active, and **another application** active for 12 s. So the documented focus gating did not appear for a process that owns windows: the Settings sheet needs no paused state, and Casso's own activation gate (FR-033) is what stops input, not XInput. One console run with no window of its own read 0 changes/s over 20 s; whether that was window-less gating or the user's partial stick movement was not pursued, since Casso always owns a window.
- **Rejected**: background input through DirectInput for Xbox controllers (combined triggers while unfocused); raw HID reports (per-model report parsing).

## R3. Threading: one dedicated controller thread

- **Decision**: a `ControllerInputThread` owns the thread and its wait loop. The backend (`Win32ControllerBackend`), created and called only on that thread, owns the message-only window, the device notifications, the DirectInput interface and devices, and all XInput and DirectInput reads (contracts/controller-backend.md). It publishes each processed sample to the game port. The sample rate is set by R13.
- **Rationale**: the UI thread's per-frame hook (`TryPresentUiFrame`, `CassoEmuCore/Shell/EmulatorShellPresent.cpp:552`) does not run while the machine is idle (`WaitForFrameOrMessage`), and pauses in modal loops. DirectInput acquisition, hot-plug notifications and XInput slot backoff also want one owner with its own message window. Microsoft documents no thread affinity for DirectInput polling; creating, acquiring and polling on one thread with its own window is the conservative arrangement.
- **COM**: `DirectInput8Create` needs no `CoInitializeEx`; the thread calls `CoInitializeEx (COINIT_MULTITHREADED)` anyway, tolerating `RPC_E_CHANGED_MODE`, since DirectInput internals are COM objects.
- **Alternatives**: `WM_TIMER` on the UI window (paused by modal loops, coarse); polling from the CPU thread (couples input to emulation speed and pause state, contradicting the spec's pause edge case).

## R4. Hot-plug detection

- **Decision**: `RegisterDeviceNotification (GUID_DEVINTERFACE_HID, DEVICE_NOTIFY_WINDOW_HANDLE)` on the thread's message-only window. On `DBT_DEVICEARRIVAL` or `DBT_DEVICEREMOVECOMPLETE`, rescan at +300 ms and again at +2 s, since not every API reflects a change immediately (SDL2 does the same). The rescan covers both DirectInput and the four XInput slots: Xbox controllers also present HID interfaces (their paths carry `IG_`, R5), so their arrivals raise the same notification. **Empty XInput slots are never polled on a timer.** Only slots found connected by a rescan are read; a read returning `ERROR_DEVICE_NOT_CONNECTED` marks the slot empty immediately, whichever of that and the removal notification comes first. With nothing connected the thread waits on its message queue with no timeout.
- **Measured 2026-09-11**: an Xbox Series X|S controller raised a HID arrival when powered on over Bluetooth and a removal when powered off, and the same pair on USB plug and unplug, all received on a message-only window. Unplugging it while it was still powered on produced a removal followed 2.3 s later by an arrival over Bluetooth: a removal is not always a disconnect, and the same controller can return under a different unit identity.
- **Still UNVERIFIED, and untestable on this machine**: whether an Xbox 360 wireless receiver raises a notification when a controller powers on. This machine has no receiver; the only 360 controller here is wireless with a Play & Charge cable, which carries power only (Windows enumerates 045E:028F with no child devices and no HID interface, so no API sees a controller). **Fallback kept as a contingency**: if a receiver is found to raise nothing, then while a receiver of that vendor and product ID is attached, and only then, its unconnected XInput slots are rechecked every 2 s. Microsoft's guidance is to recheck empty slots every few seconds at most ([Getting Started with XInput](https://learn.microsoft.com/en-us/windows/win32/xinput/getting-started-with-xinput)).
- **Measured 2026-09-12, Bluetooth reconnect**: an Xbox Series X|S controller dropped and restored with airplane mode raises `DBT_DEVICEREMOVECOMPLETE` on removal and `DBT_DEVICEARRIVAL` on return, on the same HID interface registration Casso uses, and `XInputGetState` reports the slot connected **3.5 ms** after the arrival -- well inside the +300 ms rescan. The decision above holds as it stands. A reconnect that looked missed was two other faults: a saved selection corrupted to `dinput:dddd:dddd` that no controller could match, and the picker not being told of a device-list change that moved neither the selection nor the active controller (fixed in `7118a2cc`). A 2 s XInput slot recheck built for the supposed miss was withdrawn (`0a7bbcba`).
- **Rationale**: `IDirectInput8::EnumDevices` is slow enough that polling it is wasteful; notifications cover USB, Bluetooth and the Xbox wireless adapter, since all present HID interfaces.
- **Alternatives**: `CM_Register_Notification` (callback on a system thread, reports no already-present devices; no advantage once the thread has a window anyway).

## R5. Keeping Xbox controllers out of the DirectInput list

- **Decision**: during DirectInput enumeration, read `DIPROP_GUIDANDPATH` for each device and skip any whose path contains `IG_`.
- **Rationale**: current SDL2 uses this; it needs no WMI. Bluetooth Xbox controllers also carry `IG_` in their paths.
- **Alternatives**: Microsoft's WMI sample (slow, COM security setup); `GetRawInputDeviceList` plus VID/PID matching against `guidProduct.Data1` (works, but two lookups where one suffices).

## R6. Recognizing controllers

- **DirectInput model**: `DIPROP_VIDPID` (`LOWORD` vendor, `HIWORD` product). Model key `vid:pid`.
- **DirectInput unit**: the HID serial number from `HidD_GetSerialNumberString` on the `DIPROP_GUIDANDPATH` path when it is nonempty; otherwise `DIDEVICEINSTANCE::guidInstance`, documented as reusable on the same computer ([DIDEVICEINSTANCE](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee416610(v=vs.85))). Whether `guidInstance` survives a port change is **UNVERIFIED**; the spec's model-level fallback already covers a unit that is not recognized. **Measured 2026-09-11**: the one DirectInput device on this machine, a VKBsim Gladiator (231D:0121), reports **no serial number at all**, so it falls to the instance GUID and the fallback is the ordinary path for it, not an edge case. Its `SetEventNotification` fires reliably (4,236 events over 4,283 reads) and `DIDC_POLLEDDEVICE` is clear, confirming R13's event-driven wait for DirectInput devices.
- **An enumerated axis is not necessarily a connected control.** The Gladiator's rudder pedals are a separate device that plugs into the stick; with them unplugged, their axes still enumerate and read pinned at a rail (-32768 or 32767) rather than at center. So `EnumObjects` reporting an axis says the device advertises it, not that hardware is behind it. Consequences, both in FR-007 and FR-021's rules: automatic calibration MUST NOT widen an axis's limits from a value that never moves, and `DefaultMapping` MUST prefer the primary X/Y axes rather than the first axes enumerated, or a game reads a control jammed hard over. An axis resting at a rail is also why the deadzone is measured from the calibrated center, not from zero.
- **XInput model**: one key for every Xbox-class controller, with no vendor or product in it (FR-018a, owner decision 2026-09-11). **Measured** on this machine: the same Xbox Series X|S controller reports 045E:**02FF** over USB and 045E:**0B13** over Bluetooth (and its USB composite parent is 0B12), so a key built from those IDs would split one controller's profiles three ways. XInput also forces a single fixed layout on every controller it supports, so a per-model key would buy nothing. `XInputGetCapabilitiesEx` (ordinal 108 of `xinput1_4.dll`, undocumented, present and working here) is therefore needed only for the display description, not for the key; when it is missing, the description falls back to "Xbox Controller".
- **XInput unit**: the slot, 0-3, which is the only identity XInput exposes (FR-018a). Every connected slot enumerates as its own device, so two Xbox controllers are two units over one model key. A slot is assigned in connection order and can change across a replug, so it identifies a controller only while it stays plugged in; that is acceptable, since calibration is the only per-unit data and Xbox-class controllers need none.

## R7. Normalized sample and control identity

- **Decision**: both backends deliver one normalized sample: axes as `float` in [-1, 1] (DirectInput ranges set to [-32768, 32767] with `DIPROP_RANGE`, XInput thumbs native), triggers in [0, 1], buttons as a bit set, and each POV hat decoded into four D-pad directions (hundredths of a degree, centered when `LOWORD (pov) == 0xFFFF`; diagonals set two directions). Controls are identified by a stable `ControlId { kind, index }` so a mapping written against one sample layout reads the same control next launch.
- **DirectInput data format**: `c_dfDIJoystick2` (`DIJOYSTATE2`); its fixed slots (X, Y, Z, Rx, Ry, Rz, two sliders, four POVs, 128 buttons) cover every device class in scope. `EnumObjects` records which slots the device actually reports, so the Controllers page lists only real controls (FR-020).
- **Xbox control table**: left stick X/Y, right stick X/Y, LT, RT, D-pad (4), A, B, X, Y, LB, RB, Back, Start, LS, RS. Guide is excluded (spec).
- **Rationale**: every rule in the spec (deadzone, calibration, mapping, capture) is then a pure function over this sample, testable with synthetic data, and the Win32 code only decodes.

## R8. Deadzone

- **Where a deadzone can come from**: no device reports one. XInput publishes recommended constants in `Xinput.h` for the application to apply. DirectInput's `DIPROP_DEADZONE` is a setting the application writes (default 0), not a value the device reports; separately, DirectInput by default returns values adjusted by the calibration the user set in Windows' Game Controllers control panel, which covers rest-center error on devices the user has calibrated there.
- **Decision**: default deadzone for Xbox-class sticks is XInput's published `XINPUT_GAMEPAD_LEFT_THUMB_DEADZONE` (7849 of 32767, about 24%). DirectInput has no published value, so Casso chooses 12% of travel as its default; that number is Casso's choice, adjustable per model on the Controllers page, and not a Windows value. Deadzone is **radial** when PDL0 and PDL1 are driven by the X and Y axes of the same stick, as Microsoft's sample applies it, and **axial** otherwise (a single axis, or axes from different sticks). Output is rescaled so the edge of the deadzone maps to center and full deflection still reaches 0/255 (FR-004, FR-006). Analog-to-button threshold defaults to `XINPUT_GAMEPAD_TRIGGER_THRESHOLD` (30 of 255) for triggers and 50% deflection for axes.
- **Alternatives**: axial everywhere (square-ish rest region causes cardinal-direction sticking on diagonals).

## R9. Combining input sources on the game port

- **Finding**: today the writers overwrite each other. `UpdateJoystickButtonsFromKeys` ORs X/Z with Alt, but `ApplyAppleModifierKeys`, `PushPaddleButton`, `ReleaseGuestKeys` and `StopPaddleCapture` each write the buttons directly (`CassoEmuCore/Shell/Window/EmulatorWindowInput.cpp:1802`, `:3085`, `:1705`, `:2960`). A fourth writer on another thread would fight all of them.
- **Decision**: a `GamePortInputMixer` owns the final PDL0/PDL1/PB0/PB1 values. Each source (keyboard fire keys, Apple modifier keys, mouse paddle, controller) submits its own contribution; the mixer ORs buttons (FR-014), picks the axis owner by input mode (arrows, paddle, controller, or arrow fallback per FR-008a), and writes the machine only when a final value changes. Existing direct writes are rerouted through it. The mixer is a pure class guarded by a mutex; the machine write goes through an `IGamePortSink` so tests observe it.
- **Rationale**: FR-014 and the "releasing one does not release a button the other holds" edge case cannot be met by last-writer-wins.

## R10. Persistence

- **Decision**:

Schema in [contracts/prefs-schema.md](contracts/prefs-schema.md).
  - Per machine (`MachineInputPrefs`, `$cassoUiPrefs`): `controller` (the selection key). `controllerProfile`, the machine's active profile name before 2026-09-24, is now only read, to move it onto the saved controller once. The existing `arrowsToJoystick` and `pointerMapping` keys are unchanged, so older builds keep reading their own keys.
- **Rationale**: matches the spec's persistence assumption and reuses the round-trip and in-memory file-system test infrastructure (`UnitTest/UiTests/InMemoryFileSystem.h`).
- **Superseded in part (2026-09-27) by R19**: the per-machine `controller` and `multiplayer` keys give way to global player entries in the `controllers` section, adopted once from the launched machine. The global half of this decision stands.

## R11. Menu and toolbar entries on 032's command widgets (as shipped)

032 merged to master (`9adb949e`, `6296ded7`) and is merged into this branch. It diverged from its own contracts, so this plan follows the shipped code, not `specs/032-dxui-command-widgets/contracts/`:

- **Dropdown**: `DxuiPopupMenu` (`Dxui/Widgets/DxuiPopupMenu.h`) is the single dropdown for the menu bar, toolbar pickers and context menus; there is no `DxuiDropdown`. Items are `DxuiPopupMenuItem::ForCommand`, `ForSeparator` and `ForSubmenu (cmd, children)`, holding `const DxuiCommand *`; nested submenus and check marks (from `isChecked`) work.
- **Menu bar**: `EmulatorCommands` (`CassoEmuCore/Ui/Chrome/EmulatorCommands.h/.cpp`) owns the commands as `std::unique_ptr<DxuiCommand>` and builds the menu bar from the flat `s_kMenuEntries` table, which cannot declare a submenu; `MainMenu` calls `SetItems (BuildMenuItems())` once. `DxuiMenuBar::SetItems` may be called again and closes an open menu first. The Machine id range (40010-40019) is full, and `WindowCommandManager::OnCommand` drops ids outside its ranges.
- **Toolbar**: the Input entry is `Kind::DropDown` with `InputClusterEntry` as its custom entry. Its collapsed picker is `GetPickerItems()` (mode rows that dispatch themselves), resent with `SetDropDownItems (kIdInput, ...)` by `SyncSelectorState` when its row set changes.

**Decision**:

- A new `ControllerCommands` class (`CassoEmuCore/Ui/Chrome/`) owns controller and profile rows as `std::vector<std::unique_ptr<DxuiCommand>>`, so pointers stay valid while a dropdown is open. Rows dispatch through lambdas into the shell's controller functions rather than through `WM_COMMAND` ids, which avoids a new id range for a list whose length changes. Rows: one per attached controller plus the selected-but-disconnected controller if any (checked = selected), and one per profile of the selected controller's model (checked = active). A fixed `Controller Settings...` command gets a static id in a new range with its own `OnCommand` branch, since it belongs in the static table.
- `EmulatorMenuEntry` gains a submenu marker: a row with a `submenu` provider value, which `BuildMenuItems` expands to `ForSubmenu (cmd, provider rows)`. The Machine menu gains `Controller` and `Controller Profile` submenus and the `Controller Settings...` item. On hot-plug or profile change the shell rebuilds the rows and calls `SetItems` again, deferred until no menu is open so a device arriving never closes a menu under the user.
- `InputClusterEntry::GetPickerItems` appends a separator and the same two submenus. The expanded cluster gains a controller segment (gamepad glyph with the existing LED pattern) that selects the controller when clicked; its LED and tooltip show connected, disconnected, or arrow keys standing in (FR-008a, FR-013), driven by a new `SetControllerState` setter called from `SyncSelectorState`.
- Found during the survey, pre-existing and out of scope: `WM_CHAR` still reaches the guest while a toolbar picker is open (`specs/032-dxui-command-widgets/validation.md`).

**Update (built differently)**: the three bullets above are superseded; the survey findings they rest on still hold. No `ControllerCommands` class and no submenu marker were built. The rows live in `EmulatorCommands` beside the theme and color rows, and there is no cascade at all: one paddle-source picker sits on the command bar as `kIdPaddle`, wearing the source that drives (FR-008, FR-008b), with the Machine menu keeping the per-source toggles it already had. `DeferredMenuRebuild` was dropped with the submenu, the Machine menu having no dynamic rows to rebuild. `InputClusterEntry` is deleted rather than extended: two of its three segments were the picker's answer repeated, which left it toggling one thing, so mouse mode became a plain `kIdMouse` toggle and its monoline painters moved to `InputMonoGlyphs`.

**Superseded in part (2026-09-27) by R22**: "no cascade at all" gives way to a Player 1 row and a Player 2 row, each opening a submenu, and the separate Profiles submenu (Phase 11) folds into a section at the foot of each player's submenu. The `kIdPaddle` drop-down, the `kIdMouse` toggle and the Machine menu toggles stay.

## R13. Sample rate

- **No API recommends a rate, and neither reports a device's report interval.** The interval lives in the USB endpoint descriptor, which neither API exposes and which Bluetooth devices do not have.
- **DirectInput needs no rate: it can wake on the device's own reports.** `IDirectInputDevice8::SetEventNotification` sets an event handle whenever the device's state changes (DirectInput 8 reference, `IDirectInputDevice8::SetEventNotification`; link to be confirmed during the hardware check). The controller thread waits on those handles and reads when one fires. The exception is a device whose `DIDEVCAPS` has `DIDC_POLLEDDEVICE`, which reports nothing until `Poll` is called; those are polled on the XInput cadence below. `DIPROP_BUFFERSIZE` with `GetDeviceData` additionally delivers every button transition with a sequence number, so a press shorter than a read interval is never lost.
- **XInput has no event, only a change counter.** `XINPUT_STATE::dwPacketNumber` changes when, and only when, the controller's state changed ([XINPUT_STATE](https://learn.microsoft.com/en-us/windows/win32/api/xinput/ns-xinput-xinput_state)), so a read that returns the same packet number is skipped without further work, but the thread still has to call `XInputGetState` on a cadence.
- **Decision**: the thread waits with `MsgWaitForMultipleObjectsEx` on the DirectInput event handles and its message queue, with a timeout equal to the XInput and polled-device period. That period is set from measurement: the hardware check counts `dwPacketNumber` changes per second while the stick moves continuously, on the Xbox controller wired and wireless, and the period becomes the fastest measured interval rounded down to a whole millisecond. Timed polling applies only to the selected controller, and to the controller being viewed while the Controllers page is open; with no controller selected and the page closed, the wait has no timeout at all whether or not controllers are attached, so SC-007 holds. HID notifications still arrive in that state, which is what automatic selection (FR-032) needs; the one exception is the R4 receiver fallback, if the hardware check requires it. **Measured 2026-09-11** on this machine, Xbox Series X|S controller over USB with the stick moved continuously: 125 `dwPacketNumber` changes per second, steady, which is the 8 ms USB HID interval. The period is therefore **8 ms**. (A first attempt measured the probe's own loop rate, 64 Hz, because it slept 1 ms per iteration at the default 15.6 ms timer resolution; the sleep was removed.)
- **Rejected**: one fixed rate for every device (wakes for no new data on some, lags others); sampling once per emulated frame (ties input to emulation speed and pause).
- **Amended (2026-09-27) by R23**: "with no controller selected the wait has no timeout" no longer holds while a player on Automatic is waiting for a controller's first input. Idle XInput pads are then read every 100 ms and idle DirectInput devices wake the thread through their existing events. The 8 ms period still applies only to controllers that hold a slot.

## R14. Paddle games: rate-mode axis bindings

- **Finding**: an absolute binding makes a self-centering stick a poor paddle. Releasing the stick sends the paddle back to the middle, and the paddle's whole travel maps onto the stick's short throw. A real paddle is a knob that stays where it is left, which is why mouse-to-paddle accumulates motion.
- **Decision** (owner): an analog axis binding has a `Rate` response in addition to `Absolute`. In rate mode, deflection beyond the deadzone moves the paddle value at a speed proportional to deflection, up to a per-binding maximum in paddle units per second, and the value holds when the stick is released. The accumulated value is integrated on the controller thread from the elapsed time between samples, clamped to [0, 255], and reset to center when the selection, profile, or machine changes. A built-in "Paddles" template, offered when creating a profile, binds left stick X in rate mode to PDL0, right stick X in rate mode to PDL1, and A and B to PB0 and PB1.
- **Rejected**: absolute only (unusable for paddle games on gamepads); a separate controller paddle input mode (a second place to configure the same thing profiles already hold).

## R15. PB2

- **Finding**: the machines already model the line, with different meanings per machine.
  - ][ and ][+: `AppleGamePort` handles PB2 at `$C063` (`CassoEmuCore/Machines/Apple2/Common/AppleGamePort.h:18`, `SetButton` index 2).
  - //e: `$C063` bit 7 reads the Shift key, the shift-key modification (`CassoEmuCore/Machines/Apple2/Apple2e/Apple2eKeyboard.cpp:92`). On real hardware the game-port PB2 pin and that modification share the line.
  - //c: `$C063` is the built-in mouse button, active low, and the //c's game port has no PB2 pin.
- **Decision**: PB2 is a mapping target on the ][, ][+ and //e. On the //e it ORs with Shift through the mixer, matching the shared line, so software reading Shift through `$C063` sees a controller PB2 press as Shift, as it would on the hardware. On the //c the PB2 target is shown as unavailable and bindings to it are ignored, so a controller cannot press the mouse button. PB2 has no default binding.
- **Rationale for the earlier exclusion being wrong**: it was scoped out as rarely used without checking the emulator, and the line already exists on two of the three machine families.

## R16. Automatic ordering, and when a slot counts as playing (FR-032, FR-042)

- **Decision**: a new pure class, `PlayerSlotPolicy` (`CassoEmuCore/Controllers/PlayerSlotPolicy.h/.cpp`), computes both slots from four inputs: the two player entries, the attached devices, a **connection log** and an **input log**. The service records both logs on the controller thread and hands them to the policy, which reads no device and no clock.
  - The connection log lists, in order, each distinct controller that arrived after the startup enumeration. A controller that is returning to a held slot (R17) is not added, and neither is one already in the log, so a wireless pad that sleeps and wakes does not count twice (spec edge case).
  - The input log lists, in order, each controller that gave its first **real input** while Casso was active (FR-033).
- **Ordering**: controllers a player has picked are left out of both logs' candidates. If the connection log holds two or more candidates, the first two fill the Automatic slots in log order. Otherwise the input log fills them in its order. With no input yet and exactly one candidate attached, that candidate fills Player 1 at once (FR-032) as a **provisional** holder: it drives the game port, and it gives way if a different controller gives real input first, since from that point the input order applies. With two or more candidates attached and no input, no Automatic slot is filled (spec edge case, several attached at launch).
- **Real input** is a button or D-pad direction pressed, a trigger past its button threshold (R8, `XINPUT_GAMEPAD_TRIGGER_THRESHOLD`), or any axis outside its deadzone after calibration. The deadzone already defines rest for that controller, and an axis beyond it moves an analog game's paddles, so the same edge marks use. A worn stick that drifts past its deadzone is already a problem in games, fixed by calibration or a larger deadzone. The test lives in `PlayerSlotPolicy::IsRealInput`. (Amended 2026-09-27: an earlier draft used 50% of travel; the owner chose the deadzone edge.)
- **In use**: a slot filled by Automatic is in use once its holder is in the input log; a picked slot is in use as soon as its controller is attached; the keys and the mouse are in use as soon as they are picked. The provisional Player 1 is assigned and drives the port at once, but is not in use until it gives input. If another controller arrives before any input, the first controller to give input takes Player 1, whether it is the provisional holder or the newcomer. Only slots in use count for the one-playing rule and the split in R17.
- **Start over**: when no slot's controller is playing and none is held, the policy clears the Automatic slots and both logs of every controller that holds no slot (FR-040). Picked entries are never rewritten (FR-040, FR-041).
- **Rationale**: the connection log gives a newly plugged pair a deterministic order (SC-014); the input log keeps an always-attached stick from coming ahead of the pad the user picks up (SC-013). Keeping both logs in the service and the ordering in a pure class lets every sequence in User Story 7 run as a unit test against `FakeControllerBackend` and an injected clock.
- **Alternatives**: enumeration order (rejected: the stick that is always plugged in wins every launch); connection order alone (rejected: at launch nothing has connected, so it has no answer); counting a picked controller's input toward the Automatic order (rejected: FR-042 limits Automatic to controllers no player picked).
- **Supersedes** the automatic half of the Phase 4 selection policy (`ControllerSelectionPolicy::Evaluate`, `SelectionChangeReason::AutomaticSelection`) and its rule that a connecting controller turns off arrows-to-joystick and mouse-to-paddle (FR-032 as revised; clarification of 2026-09-11 reversed).

## R17. A leaving player's slot is held; the one-playing rule (FR-040, FR-042)

- **Decision**: when a slot's holder disconnects, its paddles center and its buttons release within one tick (FR-010). If the other slot still counts as playing, the slot becomes **held** for that unit: it plays nothing and is kept for the controller that left, which takes it back on return. A held slot counts as occupied for the one-playing rule below, so the player who remains keeps exactly the lines their own target gives them and is not widened onto the leaver's paddles or buttons (FR-040). When the remaining player also stops playing, nothing is held any more and R16's start over applies.
- **One-playing rule**: when exactly one slot counts as playing and the other is neither playing nor held, the playing controller drives PDL0, PDL1 and PB0-PB2 from its profile's `pdl0`, `pdl1` and `pb0`-`pb2` bindings, whatever its slot's target (FR-042, FR-039's last sentence). When both count as playing, or one plays and the other is held, each drives what its target maps to (R18).
- **Precedence**: FR-042 read alone would widen the remaining player to everything once the other leaves; FR-040 says the remaining player keeps only what they had. The held state is how both hold: the one-playing rule applies only when the other slot is empty, not when it is held.
- **Where**: `PlayerSlotPolicy` reports each slot's state (`Empty`, `Provisional`, `Waiting`, `Playing`, `Held`); `ControllerInputService::BuildMergedLocked` turns states and targets into the merged `Controller` contribution. The mixer is unchanged.

## R18. Button lines follow the slot's target, and the target follows the profile (FR-039, FR-043)

- **Buttons**: while both players are in play, each slot's buttons are routed by its target, as the hardware wires them:

  | Target | Paddles | Buttons |
  |---|---|---|
  | Joystick 0 | PDL0, PDL1 | `pb0` to PB0, `pb1` to PB1 |
  | Joystick 1 | PDL2, PDL3 | `pb0` to PB2 |
  | Paddle 0 | PDL0 | `pb0` to PB0 |
  | Paddle 1 | PDL1 | `pb0` to PB1 |
  | Paddle 2 | PDL2 | `pb0` to PB2 |
  | Paddle 3 | PDL3 | none |

  Bindings with no line in the slot are kept in the profile and ignored. The table is a pure lookup, `PlayerTargetRules::GetButtonRoute (target)`, in `CassoEmuCore/Controllers/PlayerTargetRules.h/.cpp`. The //c never offers Joystick 1 or Paddle 2-3 (FR-035), and the sink already leaves PB2 alone there (R15). This replaces the Phase 9 rule, player one on PB0 and player two on PB1, which took player one's second button away in a two-joystick game.
- **Target from the profile**: unless the user has set the slot's target on the Controllers page, `PlayerTargetRules::GetAutomaticTarget` derives it from the holder's **active** profile: a mapping with a `pdl0` binding and no `pdl1` binding plays as a single paddle, any other as a joystick. Player 1 takes Joystick 0, or Paddle 0 as a paddle. Player 2 takes Joystick 1, or as a paddle the lowest paddle Player 1 does not hold: Paddle 1 beside a paddle, Paddle 2 beside a joystick. The target is recomputed whenever the active profile changes, including when the Joyport mode switches the active profile (spec 036). A target the machine lacks plays nothing (FR-035). `ControllerSelectionPolicy::Normalize` still runs over the result, so a user-set target and a derived one cannot overlap (FR-036).
- **Rationale**: two players who each pick a paddle profile get a two-paddle game without opening Settings (US7 #11), and one table serves joystick and paddle games alike.
- **Alternatives**: a per-slot "paddle mode" switch (rejected: a second place to say what the profile already says); keeping one button line per player (rejected by the owner, GH #156).

## R19. Global player entries, adopted once from the launched machine (FR-011, FR-037)

- **Decision**: the two player entries, each slot's user-set target and the last holder of each slot (R21) are saved globally, in the existing `controllers` section of `GlobalUserPrefs`, under new keys `players` and `lastHolders` ([contracts/prefs-schema.md](contracts/prefs-schema.md)). Player 1's keys and mouse-as-paddle entries are part of `players`; the //c IOU mouse toggle (`pointerMapping` of `mouse`) is not a player entry and stays per machine.
- **One-time adoption**: at launch, when the `controllers` section has no `players` key, the entries are built from the launched machine's `$cassoUiPrefs`: `arrowsToJoystick` true gives Player 1 the keys; a `pointerMapping` of `paddle` gives Player 1 the mouse. A saved `controller` does NOT become a pick: it becomes Player 1's last holder only (R21), and Player 1 stays on Automatic, because the old selection was usually made automatically and a pick would take Automatic away from the user without their asking. A `multiplayer` block with `enabled` true was set up by hand, so it gives both players their slots' controllers as picks, with each slot's `maps` as its user-set target. Anything not covered is Automatic. The result is written at once, so the presence of `players` marks the adoption as done and it never runs again. (Amended 2026-09-27 by the owner.)
- **Other machines' keys are dropped by being ignored**: this build neither reads nor writes `controller` or `multiplayer` for selection, and does not delete them, so an older build reading the same file keeps its own behavior. The one exception is FR-029's legacy profile move, which still reads a machine's `controller` token when that machine loads, only to key the move of `controllerProfile` (unchanged from T115).
- **Rationale**: the entries describe the controllers on the desk, not the emulated machine (FR-011), the same reason profiles and calibration are global. A single new key means no older build loses data.
- **Alternatives**: adopting every machine's selection (rejected by the spec: they would conflict); deleting the per-machine keys (rejected: an older build on the same prefs would lose its selection for nothing).

## R20. Notices stack in a Dxui control; the shell keeps the thread hand-off and the anchor (FR-044)

- **Finding**: `DxuiTimedInfoBanner` (`Dxui/Widgets/DxuiTimedInfoBanner.h`) holds one notice; `Show` replaces the text and restarts the countdown. `EmulatorShell` owns one (`m_notice`), shows it through `ShowNotice` on the UI thread, hands text over from other threads through `PostNotice` (`WM_APP_SHOW_NOTICE`), and lays it out in `SyncNotice` under the last docked band (`ComputeTopOverlayEdgePx`), all in `CassoEmuCore/Shell/EmulatorShellPresent.cpp`. Menus open over `DxuiPopupMenu::kRevealMs` (150 ms) with a quadratic ease-out that `DxuiPopupHost` applies inline and that equals `DxuiAnimation::ApplyEase (DxuiTweenEase::EaseOut, t)`; both are gated by `DxuiSystemSettings::AreMenuAnimationsEnabled()`.
- **Decision**: a new `DxuiNoticeStack` (`Dxui/Widgets/DxuiNoticeStack.h/.cpp`, an `IDxuiControl`) owns a list of `DxuiTimedInfoBanner` entries. `Push (text, nowMs)` appends one below those showing; each keeps its own full duration; `Tick (nowMs)` removes each at its own expiry and starts a slide for the notices below it, which move up into the freed place over the menus' open duration and easing, or jump when menu animations are off. `Layout` places the notices from the top of the bounds it is given, using each one's measured height. The stack reports whether it is still animating and when its next expiry falls, so the shell can keep frames coming only while something moves. The clock is passed in, as `DxuiTimedInfoBanner` already does, so every rule is a unit test.
- **Shared motion**: the duration and the curve come from one place, a small `DxuiSlide` value type (`Dxui/Core/DxuiSlide.h/.cpp`) that samples an offset from a start time, a distance, `DxuiPopupMenu::kRevealMs` and `DxuiTweenEase::EaseOut`, and returns the end at once when menu animations are off. The flag is passed in by the caller from `DxuiSystemSettings::AreMenuAnimationsEnabled()`, never read inside, because that singleton reads the real system and the CI runner reports animations off. The Controllers page's Multiplayer slide (FR-037) uses the same type.
- **The split**: Dxui owns arrival, timing, expiry, stacking order and the slide. The shell keeps what only the shell knows: the hand-off from other threads (`PostNotice` is unchanged), the anchor edge under the docked chrome, the DPI, and the redraw request. `ShowNotice` becomes a `Push`; every existing caller (disconnect, screenshot, write-protect, Caps Lock, desk scene fallback, CPU trace) goes through the stack unchanged, as FR-044 requires.
- **Alternatives**: a queue that shows one notice at a time (rejected: a later notice would wait, or shorten the earlier one's time); stacking in the shell (rejected: the timing and slide logic is Dxui's to own and test, and a second consumer is already in view on the Controllers page).

## R21. The assignment notice shows only when a slot's holder changes (FR-044)

- **Decision**: `lastHolders` (global, R19) holds the unit token of the controller that last held each slot. It is updated whenever a slot's holder becomes a controller that differs from it, whether by the user's pick, by Automatic, or by the provisional Player 1 of R16, since FR-044 requires the last holder to be saved however it came to hold the slot. It is not cleared when a holder leaves or a slot empties. A notice "Player N: description" is shown only when **Automatic** gives the slot a controller whose unit token (FR-018) differs from the saved one; a pick never shows one. The text is composed in core (`PlayerSlotPolicy::DescribeAssignment`), so spec 036's Joyport labels can substitute there.
- **Identity**: the comparison uses the unit token as saved: `xinput/product:<vvvv>:<pppp>[:<n>]` for Xbox-class controllers and the serial or instance-GUID token for DirectInput ones, so one pad in the same slot as last time shows nothing across launches (US7 #12).
- **Rationale**: a user with one controller sees nothing at every launch; a changed order always shows.

## R22. The picker: a row per player, a submenu each, profiles at the foot (FR-008, FR-008b, FR-028, FR-041)

- **Decision**: the `kIdPaddle` drop-down lists a Player 1 row and a Player 2 row, each `DxuiPopupMenuItem::ForSubmenu` showing what is playing for that player; spec 036 adds its Joyport row. A submenu lists Automatic first (written "Automatic (description)" once it has chosen), then every attached controller and any picked controller that is not attached (checked, marked not connected), then arrows-to-joystick and mouse-as-paddle under Player 1, or Disabled under Player 2. Below a separator, when a controller is playing for that player, come a `Header` row (T111) with its description, its profiles of the mode in effect with the active one checked, and New.... Exactly one entry above the separator is checked.
- **Rows are data first**: `InputModeRules` builds the row model (`PlayerRows`) from the entries, the slot states and the devices, as pure data; `EmulatorCommands` turns it into `DxuiCommand`s, as `SetPaddleSources` and `SetProfileSections` do today. The separate Profiles submenu, the `Multiplayer` row and the "N controllers" label are removed.
- **Picks** (FR-041): a controller takes effect at once whether or not it has given input; picking a controller the other player holds returns that player to Automatic; the Machine menu's toggles set Player 1's entry (FR-008).
- **Label** (FR-008b): Player 1's description, or the keys or the mouse, or "Controller" when nothing drives the port, followed by " +1" while Player 2 counts as playing (R16). Shortening is R24's.

## R23. Watching idle controllers for their first input (FR-042, SC-007)

- **Finding**: XInput raises no input event, only `dwPacketNumber`, and `Win32ControllerBackend::ReadSample` already returns the cached sample without decoding when the packet number is unchanged (`CassoEmuCore/Seams/Win32ControllerBackend.cpp`, the XInput read). DirectInput devices already carry `SetEventNotification` handles.
- **Decision**: while a player is on Automatic and waiting for a controller (R16) and Casso is active, the service watches every attached controller that holds no slot, plus a provisional holder. An XInput pad is read every `kIdleWatchPeriodMs` = 100 ms; a DirectInput device's event handle joins the wait set and it is read when the event fires. A watched read feeds only `PlayerSlotPolicy::IsRealInput`; nothing reaches the mixer until the controller holds a slot, after which it is read at the R13 period. The watch stops when neither player is waiting, and while Casso is inactive, so input made while another application is active never claims a slot (spec edge case). `ControllerWaitSources::timeoutMs` becomes the shorter of the R13 period, when any slot holder needs polling, and the idle period, when any XInput pad is watched; with neither, the wait still has no timeout.
- **Rationale**: ten `XInputGetState` calls a second on an unchanged packet cost nothing measurable (SC-007), and a person joining a game does not notice 100 ms.
- **Cost accepted**: an XInput press and release that both fall between two idle reads is missed, and the next press claims the slot.
- **Alternatives**: reading idle pads at the R13 period (rejected: 125 reads a second per pad for a controller nobody may pick up); `Windows.Gaming.Input` or GameInput events (rejected in the Session 2026-09-12 clarification).

## R24. Middle ellipsis on the picker label (FR-008b)

- **Finding**: Dxui already fits text to a width: `DxuiTextElide::ToWidth` (`Dxui/Core/DxuiTextElide.h/.cpp`) with `DxuiElide::Tail` and `DxuiElide::PathHead`, used by `DxuiButton` and `DxuiCheckbox`. It has no middle mode. The picker's label is shortened today in characters (`InputModeRules::Shorten`, `kShortLabelLimit`, tail ellipsis), and `DxuiToolbar::GetEntryWidthPx` measures a command's label unelided.
- **Decision**: add `DxuiElide::Middle` to `DxuiTextElide`, with a count of trailing characters that are never cut, so " +1" stays whole and the ellipsis lands in the middle of the description. Give `DxuiCommand` an optional label fit (maximum width in DIPs, elide mode, kept suffix), honored by `DxuiToolbar` in both measure and paint, so the strip's layout and its painting agree on one elided string. `InputModeRules` keeps dropping a trailing vendor and product parenthetical first and stops cutting by characters.
- **Rationale**: the `DxuiTextElide` header records why characters are the wrong unit (a proportional face varies up to threefold per character), and FR-008b asks the picker's width to move as little as possible, which only a width cap delivers.
- **Alternatives**: a character-count middle cut in `InputModeRules` (rejected for the reason above); eliding at paint only (rejected: the toolbar would reserve the full width and the strip would still move).
